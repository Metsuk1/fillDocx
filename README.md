# filldocx — заполнение Word-протоколов КТ/МРТ по аудиодиктовке врача

Программа берёт аудиодиктовку врача-рентгенолога и подготовленный Word-шаблон протокола
и вписывает в шаблон **красным только то, что врач продиктовал**. Всё, чего врач не
сказал, не вписывается и не считается подтверждённым.

Работает **полностью офлайн** на одном Windows-компьютере: распознавание речи и языковая
модель запускаются локально, аудио и данные пациентов никуда не отправляются.

> Это этап 2 рабочего процесса («интеллектуальная обработка диктовки и заполнение Word»).
> Этапы 0, 1 и 4 (перенос аудио, подготовка Word по имени файла, раскладка по городам)
> остаются в существующей программе. На входе нужен документ после этапа 1.

## Как это работает

```
аудио ─► 1. ffmpeg → WAV 16 кГц, Silero VAD: фрагменты ≤ 22 с, разрез только в паузах
      ─► 2. GigaAM: текст по фрагментам с метками времени (кеш в SQLite)
      ─► 3. нормализация: числа и даты цифрами, «на» → «х», ед.Н, мм, римские цифры,
            позвонки, команды «в скобках», «под вопросом», c-r, mts; словарь исправлений
      ─► 4. разбор: Ф.И.О., дата рождения, название исследования, «контраст…», «всё на этом»,
            заключение, рекомендации, поздние дополнения
      ─► 5. локальная LLM (llama.cpp / Ollama): факты по органам в JSON строго по схеме шаблона
      ─► 6. ПРОВЕРКА ИСТОЧНИКА: цитата есть в расшифровке? числа есть в цитате?
            новые слова подтверждаются диктовкой? — иначе факт отбрасывается
      ─► 7. движок правил → операции над шаблоном (числа в слоты, новые абзацы, заключение)
      ─► 8. запись в Word точечно по run-ам: Times New Roman 14, красный, остальное не трогается
      ─► 9. окно проверки: спорные места, прослушивание фрагмента, «Подтвердить»
```

**Главный принцип.** LLM не пишет документ. Она только раскладывает продиктованное по органам
и обязана приложить дословную цитату. Код проверяет каждую цитату и каждое число, а документ
собирает движок правил. Всё, что не прошло проверку, попадает в список спорных мест в окне
программы, а в Word не попадает ничего служебного: ни предупреждений, ни сырой расшифровки.

| Ситуация | Что делает программа |
|---|---|
| Орган не упомянут | Текст шаблона остаётся как есть, без красного; в окне — «не продиктовано» |
| «Норма» | Полная нормальная фраза шаблона остаётся |
| «Норма, контуры сглажены» | Красный абзац: норма шаблона с изменённой характеристикой |
| Число не продиктовано | Место в шаблоне («составляет мм») остаётся пустым |
| Цитата не найдена / числа нет в цитате | Не вписывается, спорное место |
| Посторонний разговор | Не вписывается, видно в окне с меткой времени |
| Век года рождения неоднозначен | Не угадывается, спорное место |
| Поздняя поправка значения | Берётся последнее, расхождение — спорное место |

### Шаблоны врачей с красными вариантами (режим `fill_mode: edit`, по умолчанию)

Шаблон врача (например «КТ ОБП», «КТ ОБП 2») — полный нормальный протокол, в котором **красным**
выделены типичные варианты: холецистэктомия, стент, грыжи Шморля, «увеличена в размерах за счёт
правой доли», места для размеров. Раньше ревьюер, слушая диктовку, оставлял продиктованный
красный текст (меняя только значения) и удалял непродиктованный. Программа делает так же:

1. LLM раскладывает диктовку на дословные фрагменты по абзацам шаблона. Каждый фрагмент
   сверяется с расшифровкой; фрагмент, почти дословно совпадающий с другим абзацем, переносится туда;
   кусок про соседний орган («…селезенка 48 50 ед.Н») дублируется в абзац этого органа.
2. Абзац с фрагментами правит LLM: продиктованный вариант остаётся (с числами), непродиктованный
   удаляется, нормальный текст меняется только там, где врач сказал иначе. Абзац без диктовки
   и «X норма» правит код: красные варианты удаляются, норма шаблона остаётся.
3. Проверка: каждое число есть в диктовке или в абзаце; число в мм продиктовано как размер, а не как
   плотность; новые слова подтверждаются диктовкой; нет вставок вида «не указано». Не прошло —
   один повтор с подсказкой, затем абзац не меняется и попадает в спорные. Красный вариант, ни одного
   отличительного слова которого врач не сказал, вырезается, даже если модель его оставила.
4. Запись — по разнице «было → стало» на уровне слов: нетронутый текст сохраняет цвет и формат,
   вписанное — красным, удалённое — удаляется.
5. Заключение собирается из продиктованных пунктов (формулировки шаблона берутся, если пункт совпал);
   пункт, главное слово которого врач не произносил, не вписывается. Строка рекомендаций заменяется
   продиктованными или удаляется, если рекомендаций не было.
6. Шапка: Ф.И.О. из диктовки (написание — из имени файла, если это тот же человек; не продиктовано —
   из имени файла со спорной пометкой), дата рождения, «Контрастное вещество: КТ-скан / не введено».

Старый режим (извлечение фактов по карте шаблона и дописывание абзацев) — `fill_mode: facts`.

## Установка

Нужно: Windows 10/11, Python **3.12**, видеокарта NVIDIA (рассчитано на 4 ГБ VRAM,
например RTX 3050), 16 ГБ ОЗУ. Без видеокарты работает на CPU, но медленнее.

```bat
git clone <адрес репозитория> filldocx
cd filldocx
py -3.12 -m venv .venv
.venv\Scripts\activate

rem 1. PyTorch с CUDA — команду под вашу версию CUDA возьмите на https://pytorch.org/get-started/locally/
pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu124

rem 2. Программа + распознавание + окно проверки
pip install -e .[asr,ui,dev]
pip install git+https://github.com/salute-developers/GigaAM

rem 3. ffmpeg (если ещё нет)
winget install Gyan.FFmpeg
```

### Модели (в репозитории их нет — скачиваются отдельно, один раз)

Все веса лежат в папке `models\` (она в `.gitignore`):

```
models\
  asr\         веса GigaAM (скачаются при первом запуске; для работы без интернета
               запустите один раз при наличии сети или скопируйте веса сюда)
  llama.cpp\   llama-server.exe и dll — сборка «win-cuda» с
               https://github.com/ggml-org/llama.cpp/releases
  llm\         модель в формате GGUF
```

| Компонент | Рекомендация | Размер | Комментарий |
|---|---|---|---|
| Распознавание | GigaAM `v3_rnnt` (на диктовках У.Р. и Артёма заметно лучше `v2_rnnt`) | ~0,5 ГБ | Имя — `asr.model_name` в `config/settings.yaml`. Дообученные под врачей веса — `asr.model_path` |
| VAD | Silero VAD | входит в пакет `silero-vad` | — |
| LLM | Qwen3-4B-Instruct-2507, квантование Q4_K_M (поиск на Hugging Face: «Qwen3-4B-Instruct-2507 GGUF») | ~2,5 ГБ | Помещается в 4 ГБ VRAM. При видеокарте 8+ ГБ сравните с моделью 8B — точность извлечения выше |

Файл модели назовите `Qwen3-4B-Instruct-2507-Q4_K_M.gguf` или поправьте путь в `scripts\start_llm.bat`.

Вместо llama.cpp можно использовать **Ollama**: `ollama pull <модель>`, затем в `config/settings.yaml`
указать `llm.base_url: http://127.0.0.1:11434/v1` и `llm.model: <имя модели>`.

### Проверка окружения

```bat
scripts\start_llm.bat          rem в отдельном окне — LLM-сервер на 127.0.0.1:8080
python -m filldocx check
```

## Запуск

```bat
rem одна диктовка (документ — после этапа 1, профиль врача: ur или artem)
python -m filldocx process "D:\У.Р\Иванов кт обп С+ Уральск.mp3" "D:\У.Р\Иванов кт обп С+ Уральск.docx" -d ur

rem очередь: все пары «аудио + docx» с одинаковым именем из папки
python -m filldocx scan "D:\У.Р" -d ur
python -m filldocx run            rem фаза 1 — распознавание всех, фаза 2 — заполнение
python -m filldocx status

rem окно проверки: спорные места, прослушивание, открыть в Word, подтвердить
python -m filldocx ui

rem подтверждение из командной строки
python -m filldocx confirm 12
```

- Тип исследования определяется по имени файла (КТ ОБП = КТ АС, КТ ОГК = КТ ГС, варианты С+, С+++,
  +С, контр, кириллица/латиница) или по заголовку документа. Явно: `-t kt_obp`.
- По умолчанию (`output_mode: in_place`) заполняется сам подготовленный документ; его исходная
  копия сохраняется в `work\jobs\<№>\backup`. Повторная обработка (`--force`) начинает с этой
  копии, поэтому значения не дублируются. `output_mode: copy` — писать в `work\out`.
- Подтверждение привязано к версии файла: если документ изменили после подтверждения,
  программа снова покажет его как требующий проверки.
- Расшифровки, журналы, кеш и копии — только в `work\`, не в рабочих папках врачей.
  Журнал каждого задания: `work\jobs\<№>\journal.json` (расшифровка, ответ LLM, проверенные
  факты, операции, спорные места, время каждого шага).

### Проверка без моделей

`--asr text` вместо распознавания читает готовую расшифровку из файла рядом с аудио
(`запись.mp3` → `запись.txt`). Так можно проверить разбор, извлечение и запись в Word
на эталонных текстах. LLM-сервер при этом всё равно нужен.

```bat
python -m filldocx process "запись.mp3" "протокол.docx" -d ur --asr text
```

## Настройка

### Карты шаблонов — `config/templates/*.yaml`

Каждый шаблон описан один раз: органы в порядке протокола, якорь (начало предложения в
шаблоне), нормальная формулировка, слоты для чисел, правила формулировок.

```yaml
- id: liver
  anchor: "На полученных КТ изображениях печень"
  slots:
    cc_size: {kind: size, about: "кранио-каудальный размер", before: "составляет", after: "мм"}
    density: {kind: density, about: "плотность паренхимы", before: "плотность паренхимы", after: "ед.Н"}
- id: duodenum            # органа нет в шаблоне — отдельный абзац после поджелудочной (правило 31)
  virtual: true
  place_after: pancreas
  own_paragraph: true
```

**Важно перед боевой работой:** `kt_obp.yaml` составлен по правилам и двум эталонным протоколам;
`kt_ogk`, `kt_ppn`, `kt_gm` — черновики по правилам. Сверьте якоря и нормальные формулировки с
исходными пустыми шаблонами каждого врача. Если якорь не найден, программа ничего не впишет
и покажет это в окне проверки — в случайное место текст не попадёт.

### Словари — `config/lexicon/`

- `corrections.yaml` — типичные ошибки распознавания для обоих врачей («окно кодальный» → «кранио-каудальный»).
- `doctor_ur.yaml`, `doctor_artem.yaml` — индивидуальные ошибки каждого врача.
- `terms.yaml` — медицинские термины для нечёткого исправления слов.
- `python scripts\build_lexicon.py <папки архива>` — пополнить словарь терминов из архива проверенных
  протоколов (результат `terms_archive.yaml` подключается автоматически и в git не попадает).

## Что проверить на реальных данных

1. `python -m filldocx check` — всё «установлено», LLM-сервер отвечает.
2. `python -m filldocx transcribe <аудио> -d ur` — качество распознавания чисел и терминов.
   Ошибки, которые повторяются, — в `doctor_*.yaml`.
3. Прогон 5–10 диктовок с готовыми эталонами; сравнить документы с эталонами и посмотреть
   `journal.json`. Главные метрики — числа (размеры, плотности, даты), стороны, отрицания,
   заключение, а не процент слов.
4. Время на диктовку — в выводе `process` и в журнале (поле `timings`).

## Ограничения и что не сделано

- **Не проверено с реальными моделями.** Модели не скачивались при разработке; распознавание и
  извлечение проверены только на синтетических данных и фиксированных ответах. Нужен прогон у заказчика.
- Качество извлечения зависит от LLM. Модель 4B на 4 ГБ VRAM — минимум; проверка источника не
  даст ей вписать лишнее, но часть продиктованного может уйти в спорные места вместо Word.
- Метки времени — с точностью до фрагмента (≤ 22 с), не до слова.
- Модели не дообучаются — сознательно. Повторяющиеся ошибки распознавания конкретного врача
  исправляются словарём замен (`config/lexicon/doctor_*.yaml`), формулировки — картой шаблона и
  правилами. Это предсказуемо, проверяемо и не требует данных для обучения.
- Не реализовано: карты МРТ-шаблонов, этапы 0, 1, 4 (остаются в существующей программе).
- Подсказки «описание → заключение» (правила 35–38) только показываются в окне, в Word сами не вставляются.

## Конфиденциальность

- В репозитории нет аудио, документов и правил с данными пациентов: `.gitignore` исключает
  `*.mp3`, `*.wav`, `*.docx`, `RULES_*.txt`, `work/`, `models/`. Тестовые документы создаются
  синтетически во время тестов.
- Клиент LLM отказывается работать с нелокальным адресом, пока явно не указано
  `llm.allow_remote: true` (например, для сервера в локальной сети клиники).
